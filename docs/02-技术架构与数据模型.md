# 02 · 技术架构与数据模型

本文基于 `D:\vibe coding\自动化爆款视频采集` 源码梳理原系统的技术栈、进程运行拓扑、后台队列机制、数据库 Schema、OpenAPI 路由分布与本地文件存储模型。

---

## 一、技术栈与工程结构

- **Monorepo 管理**：`pnpm` Workspace（`pnpm-workspace.yaml`）+ Python `uv` 项目管理。
- **前端（`apps/web`）**：React + TypeScript + Vite（默认 `127.0.0.1:5173`），依赖极简（仅 `react`、`react-dom`、`@phosphor-icons/react`），开发期通过 `vite.config.ts` 将 `/api` 代理至 `VITE_API_TARGET`（默认 `http://127.0.0.1:8000`）。未使用全局状态库或 React Router，页面通过 `window.location.pathname` 与状态切换。
- **后端（`apps/api`）**：Python `>=3.12,<3.14` + `FastAPI` + `Uvicorn` + `SQLAlchemy 2.0 (Async)` + `Alembic` + `httpx` + `Pillow` + `pypdf` + `yt-dlp` + `oss2` + `tos`，可选浏览器自动化依赖 `playwright`。
- **桌面外壳（`apps/desktop`）**：Electron 44 + `electron-builder`（NSIS Windows 安装包），内置打包后端 `viral-backend.exe`（PyInstaller）、静态前端 `web/dist`、FFmpeg/FFprobe、Playwright 浏览器及 `video_extract.cjs` 脚本。

## 二、运行时进程模型与通信方式

原系统在开发/桌面环境下通常由 **3 个角色** 协同运行：

1. **Web / Electron 渲染层**：通过标准 `fetch` 请求 `/api/*`（写操作强制校验请求头 `X-Viral-Studio: 1`），使用定时轮询获取任务、采集结果、工作流运行状态与资产更新，**未使用 SSE、WebSocket 或 Redis**。
2. **FastAPI 主进程（`apps/api/app/main.py`）**：在 `lifespan` 中除提供 HTTP 服务外，还启动了 **4 个常驻后台协程**：
   - `maintain_sessions`：每 30 秒续期内存中的插件中心登录会话（`_sessions`）。
   - `maintain_media_storage`：异步巡检本地媒体并同步至阿里云 OSS / 火山 TOS。
   - `maintain_workflows`：持分布式租约（`workflow_runtime_leases`）轮询触发定时工作流计划与推进 DAG 状态。
   - `collection_worker`：专门在 API 进程内运行 `lanes=("collection",)` 的任务认领循环——**原因**：市场采集需要读取仅保存在 API 进程内存 `_sessions` 中的用户插件中心 `access_token`。
3. **独立 Worker 进程（`apps/api/app/workers/main.py`）**：通过 `run_worker(lanes=tuple(q for q in WORKER_QUEUES if q != "collection"))` 轮询数据库认领其余 6 条业务通道任务，并通过心跳协程延长 `lease_until`、每 15 秒回收超时失活任务。

## 三、后台任务队列与状态机

### 3.1 7 条业务通道（`app/domain/task_queues.py` & `app/db/job_queues.py`）
系统允许不同通道并行执行，同一通道严格串行（数据库 `claim_next` 通过子查询 `~active.exists()` 保证同通道内同时最多只有 1 个 `RUNNING` 或 `WAITING_FOR_USER` 任务）：

| 通道名 | 包含任务类型 | 运行位置 |
| --- | --- | --- |
| `creation` | `image_generate`、`article_generate`、`product_storyboard`，以及 `generation_mode == "creation"` 的 `video_generate` | 独立 Worker |
| `analysis` | `video_analyze`、`media_download`、`metric_analyze`、`keyword_extract`、`workflow_preflight`、`workflow_draft` | 独立 Worker |
| `clone` | `script_generate`，以及非 `creation` 模式的 `video_generate` | 独立 Worker |
| `collection` | `douyin_*`、`xiaohongshu_*`、`tiktok_*` 采集与会话任务 | **API 进程内嵌** |
| `wechat` | `wechat_article_publish` | 独立 Worker |
| `render` | `video_postprocess`（保证本地 `RENDER_CONCURRENCY=1`） | 独立 Worker |
| `system` | 未归类任务（如 `video_import` 等） | 独立 Worker |

### 3.2 任务类型与状态机（`app/domain/jobs.py`）
- **25 个 `JobType`**：20 个现行核心类型 + **5 个已退役兼容类型**（`RETIRED_PUBLISHING_JOB_TYPES`：`publication_copy`、`publish`、`publish_fill`、`publish_account_check`、`publish_verify`）。
- **7 个 `JobStatus`**：`queued` → `running` → `succeeded` / `failed` / `cancelled`，中间可流转至 `waiting_for_user`（人工介入）或 `retry_scheduled`（按 `available_at` 退避重试）。
- **多进程局部互斥**：在下载和探测同一源视频时按 `source_item_id` 加文件锁（`local_file_lock.py`），避免分析与复刻并发重复下载；使用本地浏览器档案时按平台与档案目录加 `browser_profile_lock.py`。

## 四、数据库模型与迁移（26 张表 / 19 个迁移）

默认库为 `.data/app.db`（`sqlite+aiosqlite`），通过 `apps/api/migrations/versions/` 下 19 个迁移文件演进（`20261008_0001` 至 `20261106_0019`）。全部 26 张表按业务域分类如下：

| 业务域 | 数据表（共 26 张） | 核心职责与注意点 |
| --- | --- | --- |
| **任务底座（1 张）** | `jobs` | 全局异步任务、JSON `payload`/`result`、租约（`lease_owner`/`lease_until`）、幂等键、软删除（`deleted_at`） |
| **采集与热度（5 张）** | `source_items`、`collection_batches`、`collection_batch_items`、`metric_snapshots`、`collection_keywords` | 采集内容去重存储、批次指标快照与排名、热度分、提取的关键词库 |
| **产品与素材（4 张）** | `products`、`product_images`、`video_assets`、`clone_drafts` | 产品及有序图片、本地视频资产（关联 `source_items`）、可编辑复刻脚本草稿 |
| **公众号发布（1 张）** | `article_publications` | 公众号文章草稿/发布记录、HTML 快照路径、封面路径、`app_id` |
| **工作流引擎（13 张）** | `workflows`、`workflow_versions`、`workflow_plans`、`workflow_triggers`、`workflow_runs`、`workflow_run_items`、`workflow_node_runs`、`workflow_operations`、`workflow_budget_reservations`、`workflow_item_ledger`、`workflow_run_events`、`workflow_commands`、`workflow_runtime_leases` | 完整 DAG 版本、计划调度、命令幂等、单条防重账本、节点与外部操作状态机、预算锁、事件审计与运行时租约；其中 `workflows`、`workflow_plans`、`workflow_commands` 已带有 `principal_ref` 字段 |
| **历史兼容（2 张）** | `publication_plans`、`publication_batches` | 旧版多平台自动发布表，仅用于保留既有库结构兼容 |

> 注：上传图片/视频/Markdown 等独立资产**不建数据库表**，而是直接在 `.data/media/uploads/` 下以原文件 + 元数据侧车文件形式存放（与 `VideoAsset`、`ProductImage`、成功任务 `Job.result` 共同聚合为前端「资产库」列表）。

## 六、本地配置、密钥保护与双库媒体索引

1. **11 类配置文件（位于 `.data/*.json`）**：
   - `ark-settings.json`、`vision-settings.json`、`generation-settings.json`、`understanding-settings.json`、`image-default-settings.json`、`clone-settings.json`、`viral-score-settings.json`、`browser-settings.json`、`storage-settings.json`、`wechat-settings.json`、`wechat-accounts.json`。
2. **操作系统级密钥保护（`app/core/local_secrets.py`）**：
   - **Windows**：使用 `CryptProtectData` / `CryptUnprotectData`（DPAPI）加密后以 Base64 存于 JSON。
   - **macOS**：写入系统钥匙串（`SecKeychainAddGenericPassword`）。
   - **Linux / 容器环境**：直接抛出 `RuntimeError`（仅支持从环境变量读取，不支持从设置页保存 API Key）。
   - **配置迁移（`/api/settings/transfer/export|import`）**：导出时解密全部密钥并以明文 JSON + `Cache-Control: no-store` 返回；导入时做事务性快照与回滚。
3. **独立的云存储同步索引库（`storage-index.sqlite3`）**：
   - `app/core/media_storage.py` 额外维护一个独立于业务库 `app.db` 的同步 SQLite 文件 `storage-index.sqlite3`，记录本地媒体相对路径与 OSS/TOS 的 `pending` / `synced` / `delete_pending` / `error` 状态，并在远端存在时按需回拉到本地 `.data/media` 缓存。
